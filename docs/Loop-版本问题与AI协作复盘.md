## 3. 典型问题拆解

### 3.1 窗口与截图

- **无边框窗口 resize**：自绘窗口没有原生边框，必须补 resize 热区、最小尺寸、初始位置。
- **截图全屏**：`window_manager.setFullScreen()` 在 frameless 窗口下是空操作，退出时还会恢复原生标题栏；改为只改 bounds，不动窗口样式。
- **最大化恢复**：仅保存 `maximize()` 不够，需要保存/恢复 Windows restore-down placement（`rcNormalPosition`）。
- **最大化截图**：`SetWindowPos` 对最大化窗口无效，截图前必须先 unmaximize，结束后恢复最大化与普通位置。
- **圆角黑块**：Flutter 只裁剪画布，不裁剪 Win32 窗口；第二窗口需要 `SetWindowRgn` 或原生透明处理。
- **圆角递归**：在 `WM_SIZE` 里无保护调用 `SetWindowRgn` 会递归触发消息循环，表现为 CPU 持续上涨/整进程卡死；必须重入保护 + 几何去重。
- **多窗口焦点**：仅 `WS_EX_NOACTIVATE` 不足，还需 `WM_MOUSEACTIVATE → MA_NOACTIVATE`、无激活显示、焦点补偿；否则点回答窗会抢主窗输入焦点/IME。

### 3.2 Agent 循环

- 旧上限 12 次工具调用正好覆盖“检索 + 写笔记”，导致运行结束前没机会更新计划/给最终回答。
- 症状看起来像“反复确认是否写入”，实际是**预算耗尽 + 计划未收尾**。
- 修复：提高预算、重复工具调用跳过、写操作返回 `note_id/committed`、计划自动完成、终止时统一收尾。
- 教训：Agent 问题不能只看模型回答，要还原工具调用序列与计划状态。

### 3.3 Markdown 与多模态

- 加粗正则先吃掉 `**...**`，内部 `$...$` 不再被公式解析；改为递归解析内联内容。
- 图片附件预览：消息表新增 attachments 元数据，复用 `/api/uploads/<id>`，不复制文件。
- 大图预览需要缩放/拖动、亮暗主题、360 窄窗适配。

### 3.4 浮窗、极简与回答窗

- v0.5.0 先做单窗口浮窗；v0.6.0 才引入独立第二顶层回答窗。
- 极简条只有输入/截图/返回，高度 52px；不能用系统 Tooltip（会被窗口裁切）。
- 回答窗只在极简形态、非空文本提交后创建；普通窗口/普通浮窗不得弹。
- 离开极简形态自动关闭回答窗，会话保留在主聊天。
- 回答窗宽度约 35%、minH 180、maxH min(70%,760)、80ms 节流、内部滚动。
- 第二窗口冷启动约 **1.0–1.1 秒**，Accepted EXCEPTION；不是死循环，等待期显示思考态。
- 多窗口状态同步采用主窗唯一数据源 + IPC 只读镜像，第二窗口不得直接连后端/写 DB。

## 4. AI 协作过程中的问题

| 问题 | 现象 | 影响 | 处理/教训 |
|---|---|---|---|
| 模型 429 | `engine_overloaded_error` | 团队成员首轮失败 | 重派原任务，不重做已完成部分 |
| 工具输入 JSON 无效 | `tool input is invalid JSON` / `MALFORMED_RESPONSE` | 运行中断、任务被标 failed | 拆分大调用；失败后检查工作树、只补未完成部分 |
| 路径门禁 | inScope 含 `..` 或目录无尾斜杠 | 已完成任务无法提交 | amend 为词法路径/目录前缀；提前按门禁规则写契约 |
| 团队 halt/取消 | 所有任务 cancelled | 需要重建任务图 | 用户明确再次请求后才 resume/新建；不假设旧状态 |
| 测试假阳性 | 等待时间不足、拖动前旧 rect、占位页漏检 | 误判 PASS/FAIL | 反事实/复跑/真实六页；未知就写限制，不伪报 |
| 性能目标误判 | 首次可见 948–1074ms 被标 PASS | 评审不通过 | 改为 EXCEPTION accepted；文档写明未达 400ms |
| 误碰正式数据 | 插件测试版冒烟曾使用正式 `Prog2_app\data` | 正式数据结构被测试改动 | 移除测试表/字段，复核 integrity/会话保留；后续全部隔离 `LOOP_DATA_DIR` |
| GitHub 网络 | 连接 reset/timeout；raw CDN 不可达 | push/Release/插件市场无法验证 | 使用可用 IP 时成功过；失败时保留本地 commit/tag，明确告知用户 |
| 输入注入限制 | 无法真实鼠标点击/中文 IME 自动化 | UI 验证只能部分自动化 | 用 widget + API + PrintWindow 覆盖；真实 IME/物理多屏写为人工限制 |
| 范围膨胀 | 多窗口/DPI/焦点问题迭代很长 | 进度慢、用户反馈“慢” | 先 spike/先冻结接口；非验收项及时砍掉；核心链路优先 |
| 修复引入回归 | 圆角补丁导致消息循环；回答窗触发范围过宽 | 新 bug | 每次修复补回归测试、测 CPU/真实闭环；不能只看静态 diff |

## 6. 经验清单

1. **先用最小可验证路径证明技术可行性**：多窗口、截图、DPI 都要先 spike。
2. **测试必须复现用户路径**：仅 widget 或 mock 不能替代真实窗口/真实鼠标。
3. **别把“测试通过”当成“产品通过”**：未知/未测就写限制。
4. **每次修复都要加回归测试**：尤其 reentrancy、性能、焦点、数据隔离。
5. **严格隔离用户数据**：所有测试/冒烟使用隔离数据目录。
6. **网络/发布失败要如实报告**：本地 commit/tag 不等于远端已发布。
7. **范围要收敛**：先交付核心闭环，非验收项和性能优化分开处理。
